## 0. 문서 기준

이 PRD는 기존에 확정된 방향인 **`오늘 뭐 챙기지?`**를 기준으로 작성한 문서다.

## 1. 제품 요약

### 1.1 한 줄 설명
**“오늘 나갈 때도, 내일 떠날 때도 빠뜨리지 않게 도와주는 체크리스트 미니앱.”**

### 1.2 핵심 사용자 가치
- 출근, 외출, 운동처럼 나가기 직전에 확인할 준비물부터 골프, 캠핑, 국내여행, 해외여행, 등산처럼 전날이나 며칠 전부터 챙겨야 하는 준비물까지 한곳에서 관리한다.
- 상황별 사전 프리셋 체크리스트를 제공해 사용자가 처음부터 목록을 만들 필요가 없다.
- 사용자는 프리셋 항목을 체크박스로 관리하고, 자기 상황에 맞게 항목을 추가·삭제·정렬할 수 있다.
- 템플릿 카드는 내부 준비 필요시간 메타데이터를 바탕으로 사용자에게는 `지금`, `오늘·내일`, `미리`의 준비 흐름으로 정렬된다. 홈 상단에는 출근/외출처럼 즉시 확인할 카드가, 아래로 갈수록 골프/국내여행/해외여행처럼 미리 준비해야 할 카드가 배치된다.
- 카드 순서는 사용자가 직접 바꿀 수 있어 반복 사용할수록 자기 루틴에 가까워진다.

### 1.3 챌린지 적합성
앱인토스 바이브코딩 챌린지 주제는 **“일상이 편해지는 순간”**이며, 공식 주제 가이드에는 다음 유형이 포함된다.
- 반복되는 일을 자동화해주는 앱
- 귀찮은 계산·기록을 대신해주는 앱
- 일상의 작은 불편을 해결하는 앱
- 생활 정보를 한눈에 보여주는 앱

`오늘 뭐 챙기지?`는 외출 직전부터 전날·며칠 전 준비까지 반복되는 기억 부담과 준비물 누락을 줄여주는 미니앱이므로 주제와 직접 부합한다. 단순 리워드성 기능이 없고, 실제 생활 문제 해결 기능이 있다.

## 2. 조사 근거

### 2.1 챌린지 조건
공식 챌린지 페이지 기준:
- 출품 기간: 2026-06-08 ~ 2026-06-30
- 출품 신청폼에는 앱 이름, 미니앱 설명, 챌린지 주제와의 연관성을 작성한다.
- 신청폼 내 `appName`은 앱인토스 콘솔에 입력한 정보와 정확히 일치해야 한다.
- 신청폼의 한줄 소개와 챌린지 주제와의 연관성은 출품 적합성 판단 기준이므로 제품 카피와 별도로 정성껏 작성한다.
- 6월 30일까지 앱인토스 콘솔에 첫 빌드 제출 필요
- 2026년 6월 8일 이전 출시된 미니앱은 출품 불가. 본 앱은 챌린지 기간 내 신규 빌드/출시를 전제로 한다.
- 테마 지면 노출: 2026년 7월 첫째 주 ~ 7월 26일
- 1차 심사: 7월 1일~7월 26일 활성 유저 수(AU)
- 최종 심사: 테마 적합성, 사용자 경험 등 완성도 종합 평가
- 제외: 단순 리워드성 미니앱, 주제 가이드 이탈 미니앱
- 완성도가 낮아 토스 유저의 사용성에 위해가 우려되면 출시 반려 가능성이 있다.
- 챌린지 참여 중 앱인토스 운영 정책 위반 시 노출 중단 및 보상 지급 제한 가능성이 있다.
- 출품작의 권리는 지원자에게 귀속되지만, 제3자 지식재산권을 침해하지 않아야 한다. 아이콘/일러스트/폰트/템플릿 문구는 직접 제작 또는 사용권이 명확한 리소스만 사용한다.

### 2.2 앱인토스 기술스택 조사
공식 개발자센터 기준:
- WebView 방식은 CSR/SSG 웹 서비스를 미니앱으로 실행하는 방식이며 React/Vue/Svelte 등 웹 개발 경험을 활용할 수 있다.
- 프로젝트 생성: `npx create-ait-app <app-name>`
- 설정 파일: `granite.config.ts`
  - 콘솔 등록 정보와 `appName`, `displayName`, `icon`, `primaryColor`를 일치시킨다.
  - MVP는 권한을 쓰지 않으므로 `permissions: []`를 기본으로 둔다.
  - WebView 개발 서버/빌드 명령은 공식 템플릿 생성 후 실제 `granite.config.ts` 기준으로 확정한다.
- 앱 식별자: `appName`; 본 프로젝트는 `what-to-bring`으로 확정한다. 딥링크는 `intoss://what-to-bring`
- 테스트용 private 딥링크: `intoss-private://what-to-bring`
- SDK: `@apps-in-toss/web-framework`
- Analytics: 공식 문서 버전 차이가 있으므로 설치 SDK 기준으로 확인한다. 현재 레퍼런스는 `Analytics.init` 후 `Analytics.Press`/`Analytics.Impression`/`Analytics.Area` 사용을 안내하고, 로그 가이드는 `Analytics.click`/`Analytics.impression` 예시도 제공한다. 구현 시 실제 패키지 타입을 기준으로 이벤트 래퍼를 만든다. 페이지 이동 로그는 자동 기록 전제
- TDS WebView 패키지: `@toss/tds-mobile`, `@toss/tds-mobile-ait`, `@emotion/react`, `react`, `react-dom`
- 로컬 저장소 API: `Storage.setItem/getItem/removeItem/clearItems`. 앱인토스 환경에서는 `AsyncStorage` 사용 금지
- 공유 API: `share({ message })`
- 빌드: `npm run build` 후 생성된 `.ait` 파일을 앱인토스 콘솔에 업로드. 앱 번들은 압축 해제 기준 100MB 이하를 목표로 하며, 이미지/폰트 등 리소스는 최소화한다.
- 테스트: 샌드박스 앱 기능 검증 후 `.ait` 업로드와 테스트용 앱스킴/QR로 실제 토스앱 최종 테스트를 수행한다. 검토 요청은 테스트를 최소 1회 완료해야 가능하다.
- 네트워크: MVP는 외부 서버가 없지만, 프로덕션에서 서버를 붙일 경우 실제 서비스 origin `https://<appName>.apps.tossmini.com`와 QR 테스트 origin `https://<appName>.private-apps.tossmini.com`의 CORS 차이를 확인한다. 샌드박스의 http 허용은 라이브 환경에 적용되지 않는다.
- 출시: 승인 후 출시하면 즉시 사용자에게 반영되므로, 출시 직전 스모크 테스트와 롤백/핫픽스 기준을 둔다.
- 검수: 운영, 기능, 디자인, 보안 검수. 평균 2~3일
- SDK는 최신 템플릿 기준을 우선한다. Analytics는 현재 레퍼런스 기준 `v1.0.3+`, 대시보드/로그 가이드 기준 `0.0.26+` 이상 조건을 모두 확인한다

### 2.3 정책 리스크
공식 정책 기준:
- 자사 앱 설치 유도 및 외부 링크 의존 제한
- 앱 내 기능은 미니앱 안에서 완결적으로 경험되어야 함
- 금융상품, 투자, 의료 예약/연결, 사행성, 가상자산, 불법/부정 조장 서비스 제한
- 생성형 AI 결과 노출은 별도 고지/검토 필요
- 다크패턴 방지: 진입 즉시 전면 바텀시트, 뒤로가기 차단용 동의 유도, 닫을 수 없는 CTA, 다음 행동을 예측하기 어려운 CTA 금지

`오늘 뭐 챙기지?`는 준비물 체크리스트이므로 정책 리스크가 낮다.  
단, `병원` 템플릿은 병원 추천/예약/의료 판단을 제공하지 않고 **사용자 개인 준비물 체크**에만 한정해야 한다.

## 3. 경쟁서비스 / 대체재 조사

| 유형 | 대체재 | 사용자가 쓰는 이유 | 약점 / 기회 |
|---|---|---|---|
| 기본 메모앱 | Apple Notes, Samsung Notes, Keep | 자유롭게 체크리스트 작성 가능 | 상황별 기본 템플릿이 없고, 매번 찾아야 함 |

| 노션/시트 | Notion, Google Sheets | 커스터마이징 가능 | 모바일에서 빠른 사용성이 낮음 |

| 날씨앱 | 기본 날씨, 네이버 날씨 | 비/기온 확인 | “그래서 뭘 챙겨야 하는지”까지 연결하지 않음 |
| 육아/등원 알림 | 어린이집/학교 앱 | 공지 확인 | 준비물 체크와 개인 루틴 관리가 분리됨 |

### 경쟁 포지셔닝
`오늘 뭐 챙기지?`는 거대한 할 일 앱이 아니라 **Toss 안에서 여는 초경량 상황별 준비물 체크 도구**로 포지셔닝한다.

핵심 차별점:
1. 상황 카드 기반이라 진입 즉시 쓸 수 있음
2. `지금`, `오늘·내일`, `미리`의 준비 흐름으로 카드가 정렬되어 즉시 확인할 루틴과 미리 준비할 루틴이 자연스럽게 구분됨
3. 프리셋 체크리스트를 제공하되 사용자가 항목과 카드 순서를 바꿀 수 있음
4. 최근 루틴 우선 노출로 반복 사용 유도
5. 별도 계정/설치/세팅 없이 MVP 사용 가능
6. Toss UI와 맞는 단순하고 신뢰감 있는 경험

### 4.2 조사 기록과 보완 기준
1차 조사는 `docs/community-painpoints-research.md`에 기록했다. 아래 키워드는 필요 시 추가 검증에만 사용한다.

- `운동 준비물 까먹음`, `헬스장 수건 까먹음`

## 5. 타깃 사용자

### 5.1 1차 타깃
- 매일 출근/등교하는 직장인/학생
- 운동 루틴이 있는 사용자
- 비 오는 날이나 외근 전 준비물을 자주 놓치는 사용자
- 골프, 여행, 캠핑처럼 전날 또는 며칠 전부터 짐을 챙기는 사용자
- 병원/약국 방문 전 필요한 것을 정리해야 하는 사용자
- 아이 등원/등교 준비물을 챙기는 보호자

### 5.2 2차 타깃
- 출장/여행이 잦은 사용자
- 퇴근길 장보기 루틴이 있는 사용자
- ADHD 성향, 건망증, 바쁜 아침 루틴으로 인해 체크리스트가 필요한 사용자

## 6. 제품 원칙

1. **준비물 누락 방지:** 제품의 중심은 일정 관리가 아니라 준비물을 빠짐없이 챙기는 체크리스트다.
2. **준비 흐름:** 홈 카드는 내부 준비 필요시간 메타데이터를 사용자 친화적인 `지금`, `오늘·내일`, `미리` 그룹으로 보여준다. 그룹명은 준비물 항목처럼 보이지 않아야 한다.
3. **사용자 변경 가능:** 사용자는 카드 순서와 체크리스트 항목을 자기 루틴에 맞게 바꿀 수 있다.
4. **한 화면 한 과업:** 홈은 준비 루틴 선택, 상세는 체크박스 기반 준비물 관리, 완료는 피드백.
5. **로컬 우선:** MVP는 로그인/서버 없이 작동.
6. **개인정보 최소화:** 민감 정보, 위치, 연락처, 의료정보 수집 금지.
7. **Toss 톤:** 짧고 직접적인 문장, 큰 CTA, 부드러운 완료감.

## 6.1 용어 정의와 홈→준비물 트리 구조

이 서비스의 정보 구조는 **홈 → 보기 모드 → 그룹 → 루틴 카드 → 준비물** 5단계로 고정한다. 카테고리는 이 중 `카테고리별 보기`의 그룹이자 검색 보조 메타데이터로 사용한다.  
홈 화면은 이 트리를 `준비 흐름별 보기` 또는 `카테고리별 보기`로 보여주는 진입점이다. 내부 데이터는 준비 필요시간 메타데이터를 쓰되, 사용자에게 보이는 그룹명은 준비물 자체처럼 오해되지 않도록 **짧은 상황형 라벨**을 사용한다.

└─ 보기 모드: 카테고리별
   ├─ 카테고리: 일상/외출
   │  ├─ 루틴 카드: 출근

### 용어 정의

| 용어 | 의미 | 예시 | 구현 기준 |
|---|---|---|---|
| 홈 | 사용자가 루틴 카드를 찾고 진입하는 첫 화면 | 최근 사용, 보기 모드, 카드 목록 | 체크리스트 편집은 하지 않음 |
| 보기 모드 | 홈 카드 목록을 보여주는 기준 | 준비 흐름별, 카테고리별 | 사용자가 변경 가능, 로컬 저장 |
| 준비 흐름 그룹 | 준비 필요시간 메타데이터를 사용자 친화적으로 보여주는 묶음 | 지금, 오늘·내일, 미리 | 그룹 순서는 기본 고정. 준비물 항목명이 아니라 루틴 카드 묶음명 |
| 카테고리 그룹 | 생활 영역 기준 묶음 | 일상/외출, 레저/여행 | 카테고리별 보기에서 사용 |
| 카테고리 | 루틴의 생활 영역 분류 | 일상/외출, 레저/여행 | 검색/탐색 보조에도 사용 |
| 루틴 카드 | 하나의 상황별 체크리스트 진입 단위 | 출근, 골프, 국내여행 | 명사형 이름 사용 |
| 준비물 | 루틴 카드 안의 체크박스 항목 | 골프화, 등산화, 충전기 | 기본 항목 + 사용자 항목으로 구성 |
| 태그 | 루틴 검색을 돕는 보조 키워드 | 골프: 라운딩, 스크린 | 카드명은 바꾸지 않고 검색 보조로만 사용 |

### 순서 변경 원칙

- 기본 홈 보기 모드는 `준비 흐름별`이다.
- 사용자는 홈 보기 모드를 `준비 흐름별` 또는 `카테고리별`로 바꿀 수 있다.
- 사용자는 **현재 보기 모드의 각 그룹 내부에서만** 루틴 카드 순서를 바꿀 수 있다.
- MVP에서는 그룹 간 카드 이동은 지원하지 않는다.
- 최근 사용 루틴은 별도 섹션으로 노출하며, 메인 카드 목록의 정렬을 바꾸지 않는다.

## 6.2 기본 템플릿과 사용자 저장 정책

기본 템플릿은 앱이 제공하는 원본 데이터이며, 사용자 변경으로 오염되면 안 된다.  
사용자 변경값은 별도 override 데이터로 저장하고, 화면에서는 `기본 템플릿 + 사용자 override`를 병합해 보여준다.

### 기본 정책

- 기본 템플릿은 앱 코드에 고정된 원본으로 유지한다.
- 사용자가 항목을 추가하거나 순서를 바꾸면 사용자 값으로 저장하고, 다음 진입 시 사용자 값 기준으로 보여준다.
- 사용자는 언제든 `기본값으로 돌리기`를 눌러 해당 루틴을 기본 템플릿 상태로 되돌릴 수 있다.
- 사용자는 `기본값에서 제공하는 준비물 보기`를 통해 원본 템플릿 항목을 확인할 수 있다.
- MVP에서 기본 항목은 삭제할 수 없다. 단, 체크/해제는 가능하다.
- MVP에서 삭제 가능한 항목은 사용자 커스텀 항목뿐이다.
- 기본 항목 숨김/삭제, 기본 항목과 커스텀 항목의 완전한 통합 정렬은 v0.2 이후 검토한다.
- 체크 상태는 기본적으로 영구 저장하지 않는다. 루틴을 다시 열면 체크 상태는 초기화된다.

### 저장/초기화 범위

| 위치 | 버튼/행동 | 범위 | 결과 |
|---|---|---|---|
| 체크리스트 | 체크박스 체크/해제 | 현재 화면 상태 | 기본적으로 영구 저장하지 않음 |
| 체크리스트 | 커스텀 항목 추가 | 해당 루틴의 사용자 항목 | 즉시 로컬 저장 |
| 체크리스트 | 커스텀 항목 삭제 | 해당 커스텀 항목 | 즉시 로컬 저장 |
| 체크리스트 | 커스텀 항목 순서 변경 | 해당 루틴의 커스텀 항목 순서 | 즉시 로컬 저장 |
| 체크리스트 | 체크만 지우기 | 현재 루틴의 체크 상태 | 항목 구성은 유지 |
| 체크리스트 | 기본값에서 제공하는 준비물 보기 | 원본 템플릿 조회 | 사용자 변경값은 바꾸지 않음 |
| 체크리스트 | 기본값으로 돌리기 | 해당 루틴의 사용자 override | 확인 후 사용자 항목/순서 변경을 삭제하고 원본 복원 |
| 홈 설정 | 카드 순서 초기화 | 현재 보기 모드의 그룹 내부 순서 | 기본 카드 순서로 복원 |
| 홈 설정 | 홈 보기 기본값으로 돌리기 | 홈 보기 모드 | `준비 흐름별`로 복원 |
| 설정 | 저장된 변경값 모두 삭제 | 전체 로컬 저장 데이터 | MVP에서도 제공. 확인 후 사용자 항목/카드 순서/최근 사용을 삭제하고 기본 템플릿만 유지 |

# 7. MVP급 PRD

## 7.1 MVP 목표
6월 30일 첫 빌드 제출을 목표로, **상황별 프리셋 준비물 체크 + 홈 검색(B안) + 사용자 커스텀 + 홈 보기 모드 설정 + 그룹 내부 카드 순서 변경 + 최근 루틴 저장 + 토스 콘솔/Analytics 기반 측정**까지 구현한다.

## 7.2 MVP 사용자 시나리오
1. 사용자가 미니앱에 진입한다.
2. 홈에서 사용자가 선택한 보기 모드에 따라 정리된 템플릿 카드를 본다. 기본 보기 모드는 준비 흐름별이다.
   - `지금`: `출근`, `외출`, `운동`처럼 바로 확인할 카드
   - `오늘·내일`: `비 오는 날`, `병원`, `장보기`, `등원/등교`처럼 가까운 일정 카드
   - `미리`: `골프`, `캠핑`, `국내여행`, `해외여행`, `등산`처럼 미리 준비하면 좋은 카드
3. 사용자는 홈 보기 모드를 `준비 흐름별` 또는 `카테고리별`로 바꿀 수 있다.
4. 현재 보기 모드의 각 그룹 안에서 카드 순서를 사용자 기준으로 바꿀 수 있다.
5. 사용자는 검색창에 `라운딩`, `해외`, `검진` 같은 표현을 입력해 카드명/태그 기준으로 루틴 카드를 찾을 수 있다.
6. 사용자는 필요한 템플릿 카드를 고른다.
7. 체크리스트 바텀시트에서 프리셋 준비물을 체크박스로 관리한다.
8. 필요한 경우 커스텀 항목을 추가·삭제·정렬한다.
9. 홈 카드 순서가 마음에 들지 않으면 사용자 기준으로 바꾼다.
10. 진행률을 확인한다.
11. `체크만 지우기`, `기본값에서 제공하는 준비물 보기`, `기본값으로 돌리기`를 필요에 따라 사용한다.
12. 다음 방문 시 최근 사용 루틴이 홈 상단의 별도 섹션에 표시된다.

  - 등산
- 홈 검색(B안): 카드명과 태그를 대상으로 하는 클라이언트 검색을 제공한다.
  - placeholder: `어떤 준비를 찾고 있나요?`
  - 검색 대상: 루틴 카드명, 카테고리명, 검색 태그
  - 예: `라운딩`, `스크린` 검색 시 `골프`, `해외`, `공항`, `여권` 검색 시 `해외여행` 노출
  - 검색 결과는 현재 보기 모드와 무관하게 관련도 높은 카드 리스트로 보여준다.
  - 빈 결과 안내: `아직 맞는 루틴이 없어요. 직접 항목을 추가해 볼까요?`
- 홈 보기 모드는 사용자가 설정할 수 있다.
  - 기본값: 준비 흐름별
  - 선택값: 카테고리별
- 준비 흐름별 정렬은 다음 구조를 기본으로 한다.
  - `지금`: 나가기 직전 바로 확인하는 루틴 카드
  - `오늘·내일`: 당일/전날 일정에 맞춰 확인하는 루틴 카드
  - `미리`: 며칠 전부터 준비하면 좋은 루틴 카드
- 카테고리별 정렬은 다음 구조를 기본으로 한다.
  - 일상/외출
  - 건강/운동
  - 가족/생활
  - 업무/출장
  - 레저/여행
- 사용자는 현재 보기 모드의 각 그룹 안에서 카드 순서를 직접 바꿀 수 있다.
- 보기 모드와 그룹 내부 카드 순서는 로컬 저장한다.
- 최근 사용 루틴 1~3개를 별도 섹션으로 노출한다.
- 최근 사용 루틴은 메인 카드 목록의 정렬 순서를 바꾸지 않는다.
- 빈 상태: `최근 쓴 루틴이 여기에 보여요`

### F2. 체크리스트 바텀시트
- 준비물 상세 진입은 별도 전체 페이지가 아니라 **바텀시트**를 기본으로 한다.
- 홈 카드 탭 시 하단에서 체크리스트 바텀시트가 올라온다.
- 바텀시트는 1차 높이 70~80%로 열고, 필요 시 전체 높이로 확장한다.
- 뒤로가기/스와이프 처리 우선순위는 `검색 입력 focus 해제 → 열린 바텀시트 닫기 → 홈에서 미니앱 기본 뒤로가기/닫기` 순서로 둔다.
- 체크 상태는 바텀시트가 열려 있는 동안만 유지한다. MVP에서는 바텀시트를 닫고 같은 루틴을 다시 열면 체크 상태를 초기화한다. 커스텀 항목/순서만 Storage에 저장한다.
- 상황별 제목
- 기본 준비물 리스트
- 체크박스 기반 체크/해제
- 진행률 표시: `5개 중 3개 완료`
- 완료율 progress bar
- 체크만 지우기 버튼
- `기본값에서 제공하는 준비물 보기`는 바텀시트 안의 보조 액션으로 제공한다. 누르면 원본 템플릿 항목만 읽기 전용으로 보여준다.
- `기본값으로 돌리기`는 권장안대로 해당 루틴의 사용자 변경값만 삭제하며, 사용자 변경값이 있을 때만 노출한다.
- 바텀시트 닫기

### F3. 커스텀 항목
- 사용자가 항목 직접 추가 가능
- 커스텀 항목 삭제 가능
- 커스텀 항목 순서 변경 가능. 형 확정사항: 커스텀 항목 순서 변경은 MVP 범위에 포함한다.
- 커스텀 항목은 해당 상황에 저장
- 기본 항목은 삭제 불가
- 기본 항목과 커스텀 항목의 완전 통합 정렬은 MVP 제외
- 빈 값 입력 방지
- 중복 항목 입력 시 안내

### F4. 홈 보기 모드 설정과 카드 순서 변경
- 기본 홈 보기 모드는 준비 흐름별이다.
- 사용자는 홈 보기 모드를 바꿀 수 있다.
  - 준비 흐름별
  - 카테고리별
- 현재 보기 모드의 각 그룹 안에서 카드 순서를 직접 변경할 수 있다.
- 변경된 보기 모드와 그룹별 카드 순서는 로컬 저장한다.
- MVP에서는 복잡한 드래그 UI 대신 `위로`, `아래로` 버튼 또는 편집 모드 기반 순서 변경을 허용한다.
- `카드 순서 초기화`로 현재 보기 모드의 기본 카드 순서로 되돌릴 수 있다.
- `홈 보기 기본값으로 돌리기`로 보기 모드를 `준비 흐름별`로 되돌릴 수 있다.

### F5. 최근 사용 루틴 저장
- 사용자가 체크리스트를 열면 해당 상황을 최근 사용 루틴으로 기록
- 최근 사용 순으로 최대 3개 홈 상단의 별도 섹션에 노출
- 메인 카드 목록에는 같은 루틴 카드를 그대로 유지한다.
- 최근 사용은 메인 카드 순서 변경이나 개인화에 영향을 주지 않는다.
- 앱인토스 Storage API 사용

### F6. 사용자 루틴 저장과 기본값 복원
- 기본 템플릿은 원본으로 유지하고 사용자 변경값만 별도 저장한다.
- 커스텀 항목 추가/삭제/정렬은 즉시 로컬 저장한다.
- 다음 진입 시 `기본 템플릿 + 사용자 변경값`을 병합해 보여준다.
- `기본값에서 제공하는 준비물 보기`로 원본 템플릿을 확인할 수 있다.
- `기본값으로 돌리기`는 해당 루틴의 사용자 변경값만 삭제한다.
- 체크 상태는 기본적으로 매번 초기화하되, 옵션으로 마지막 체크 상태 복원은 v0.2에서 검토

### F7. 홈 검색
- MVP에 검색을 포함한다.
- 검색은 외부 서버 없이 클라이언트에서 기본 템플릿 데이터의 `title`, `category`, `tags`를 대상으로 수행한다.
- 검색어는 소문자화/공백 정규화 후 부분 일치로 처리한다.
- 검색 결과 카드 탭 시 동일한 체크리스트 바텀시트를 연다.
- 검색어 자체는 Storage에 저장하지 않는다.
- Analytics 적용 시 `search_routine` 이벤트에 검색어 원문이 아니라 정규화된 검색 카테고리 또는 결과 수만 기록한다.

### F8. 기본 완료 피드백
- 전체 완료 시: `다 챙겼어요. 이제 나가도 좋아요.`
- 일부 완료 시: `아직 2개 남았어요.`
- 체크만 지우기 시: `체크를 모두 지웠어요.`
- 기본값으로 돌리기 시: `기본 준비물로 되돌렸어요.`

## 7.5 MVP 비기능 요구사항
- 모바일 WebView 세로형 논리 해상도 360×640 ~ 420×740을 기준으로 우선 최적화
- 첫 화면 로딩 2초 이내 목표
- 상단의 즉시형 카드는 첫 액션까지 10초 이내
- 하단의 미리 준비형 카드도 상세 진입 후 바로 체크 가능해야 함
- 터치 영역 최소 44px
- 폰트 확대 대응
- 스크린리더 레이블 제공
- 색상만으로 상태 구분 금지
- 외부 서버 없이 사용 가능
- `.ait` 번들 압축 해제 기준 100MB 이하, MVP는 대용량 이미지/영상/폰트 번들링 금지
- 샌드박스와 라이브 환경 차이를 고려해 외부 네트워크 의존 기능은 MVP에서 제외

### 7.5.1 MVP 엔지니어링 표준
- 기능 구현은 데이터/상태/뷰를 분리한다.
  - `templates.ts`: immutable `TemplateRoutine[]`
  - `storage.ts`: Apps in Toss Storage 래퍼와 schema migration
  - `search.ts`: title/category/tags 검색과 result ranking
  - `analytics.ts`: SDK 버전 차이를 흡수하는 이벤트 래퍼
  - `routineReducer.ts`: 체크 상태, 커스텀 항목, 순서 변경 reducer
- TDD 우선순위:
  1. 검색 매칭: 카드명/태그/카테고리, 빈 결과, 민감 검색어 미저장
  2. 템플릿 병합: 기본 항목 + 사용자 항목, 기본 템플릿 불변성
  3. 초기화 범위: 체크만 지우기/기본값으로 돌리기/카드 순서 초기화 분리
  4. Storage 직렬화: schemaVersion, 깨진 JSON fallback, quota/오류 처리
  5. Analytics payload: raw search query/custom item label 미포함
- 소프트웨어 개발 표준:
  - TypeScript `strict` 기준으로 작성한다.
  - 사용자 입력은 `trim`, 연속 공백 정규화, 길이 제한을 적용한다.
  - Storage read/write 실패 시 앱이 흰 화면이 되지 않도록 기본 템플릿으로 fallback하고 짧은 안내를 보여준다.
  - 모든 이벤트 payload는 allowlist 기반으로 작성하고 자유입력 텍스트를 보내지 않는다.
  - 릴리즈 전 `npm run build`, `npm test`, `npx tsc --noEmit` 또는 동등한 타입 체크를 통과해야 한다.
  - 가능하면 `npm run lint`/format check를 추가하고, 실패 시 `.ait` 업로드를 막는다.
  - `getOperationalEnvironment()`로 sandbox/toss 환경을 구분하고, 환경별 로그/안내 차이를 테스트한다.
  - 특정 SDK 기능을 쓸 경우 `isMinVersionSupported()`로 토스앱 최소 버전 충족 여부와 업데이트 안내를 검토한다.

- UI: React 18 + Vite
- SDK: `@apps-in-toss/web-framework`
- Analytics: 공식 문서 버전 차이가 있으므로 설치 SDK 기준으로 확인한다. 현재 레퍼런스는 `Analytics.init` 후 `Analytics.Press`/`Analytics.Impression`/`Analytics.Area` 사용을 안내하고, 로그 가이드는 `Analytics.click`/`Analytics.impression` 예시도 제공한다. 구현 시 실제 패키지 타입을 기준으로 이벤트 래퍼를 만든다. 페이지 이동 로그는 자동 기록 전제
- Design System: `@toss/tds-mobile`, `@toss/tds-mobile-ait`, `@emotion/react`
- Navigation/Safe Area: 기본 비게임 내비게이션 바 + `SafeAreaInsets.get/subscribe`
- Native events: `graniteEvent.addEventListener('backEvent')` for bottom-sheet/back handling, cleanup required
- Environment: `getOperationalEnvironment`, optional `isMinVersionSupported`
- Persistence: Apps in Toss Storage API. `AsyncStorage` 금지, JSON 문자열 직렬화/역직렬화 헬퍼 사용
- State: React state + reducer
- Testing: Vitest for reducer/search/storage helpers, Testing Library for 핵심 UI 상태, mobile viewport QA, Apps in Toss sandbox 실기기 테스트
- Build: `npm run build` → `.ait` upload

## 7.8 MVP 성공지표

토스 대회/출품 맥락에서는 **토스 콘솔에서 확인 가능한 지표**와 **Apps in Toss Analytics 직접 이벤트**를 기준으로 본다. 앱인토스 공식 가이드 기준으로 페이지 이동 로그는 자동 기록되며, 클릭/노출 이벤트는 `Analytics` 객체로 직접 기록할 수 있다. 구현 API는 설치 SDK 타입을 확인해 `Analytics.Press`/`Analytics.Impression` 또는 `Analytics.click`/`Analytics.impression` 중 실제 지원 형태로 래핑한다. 샌드박스/출시 준비 단계 데이터는 제공되지 않고 실제 런칭 다음 날부터 분석 화면에서 확인 가능하므로, 제출 전에는 QA 로그/수동 검증, 출시 후에는 콘솔 지표로 판단한다.

| 지표 | 측정 방식 | 목표/판단 기준 |
|---|---|---|
| DAU/AU | 토스 콘솔 대시보드 | 1차 심사 기간 활성 사용자 확보 |
| 유입경로 | 토스 콘솔 대시보드 | 검색/전체탭/기타 유입 확인 |
| 홈 카드 선택률 | `select_routine` | 홈 진입 대비 카드 선택 60% 이상 |
| 체크 시작률 | `check_item` 최초 발생 사용자 / 카드 선택 사용자 | 50% 이상 |
| 검색 사용률 | `search_routine` 발생 사용자 / 홈 진입 사용자 | 검색이 탐색에 실제 기여하는지 확인 |
| 기본값 복원 사용률 | `reset_to_default` | 템플릿/커스텀 UX 혼란 여부 확인 |
| 최근 루틴 재방문률 | `select_routine` with `source=recent` | 15% 이상 |
| 평균 완료 체크 수 | `check_item` 이벤트 집계 | 사용자당 평균 3개 이상 |
| 전환 지표 후보 | 토스 콘솔 전환 지표 직접 조합 | 핵심: `check_item` 1회 이상; 보조: `select_routine`, `search_routine`, `complete_routine` |

# 8. 프로덕션급 PRD

## 8.1 프로덕션 목표
단순 체크리스트를 넘어, 사용자의 반복 준비 상황을 학습하고 출근/외출부터 골프/국내여행/해외여행/등산까지 관리하는 **초경량 생활 준비 비서**로 확장한다.

## 8.2 프로덕션 기능 요구사항

### P0. 조사 기반 추후 업데이트 후보
커뮤니티/공개 웹 불편 사례 조사 결과, 아래 방향은 서비스 가치를 높일 수 있지만 MVP에는 반영하지 않는다. 현재 MVP는 단순한 상황별 프리셋 체크리스트, 사용자 커스텀, 검색, 최근 루틴, 순서 변경에 집중한다.

- 오늘만 항목: 이번 체크에만 필요한 임시 준비물. 예: 오늘 발표자료, 오늘 알림장 준비물, 오늘 저녁 재료.
- 고위험 항목 표시: 여권, 신분증, 법인카드, 아이 물병/수저통, 충전기처럼 빠뜨리면 피해가 큰 항목을 강조.
- 출발 전 30초 체크: 전체 체크리스트 전에 핵심 항목 3~5개만 빠르게 확인하는 모드.
- 상황별 질문: 캠핑/등산/골프/해외여행 등에서 1개 질문으로 준비물 항목을 보정하는 방식.
- 정보 수집 UX: 알림장, 카톡, 메모, 회사 공지에서 본 항목을 사용자가 쉽게 추가하는 흐름.

이 후보들은 대회 제출 후 AU, 재방문, 사용자 피드백, 구현 여력에 따라 프로덕션 확장 여부를 판단한다.

### P1. 루틴 프로필
- 사용자별 루틴 묶음 생성
  - 출근 루틴
  - 외출 루틴
  - 운동 루틴
  - 병원 루틴
  - 아이 등원 루틴
  - 골프 루틴
  - 국내여행 루틴
  - 해외여행 루틴
  - 등산 루틴
- 루틴별 기본 항목, 커스텀 항목, 정렬 순서 저장
- 루틴 복사/편집

### P2. 홈 카드 개인화
- 사용자는 홈 보기 모드를 선택할 수 있다.
  - 준비 흐름별
  - 카테고리별
- 기본 보기 모드는 준비 흐름별이다.
- 각 보기 모드의 그룹 안에서는 사용자 변경 순서를 우선 적용한다.
- 최근 사용은 별도 섹션으로만 노출하고, 사용 빈도/사용자 변경 순서는 그룹 내부 카드 순서에만 반영한다.
- 준비 흐름별 정렬에서는 상단에는 즉시 준비 카드, 아래에는 미리 준비 카드라는 정보 구조를 유지한다.
- 위치/날씨 API 없이도 로컬 사용 기록 기반으로 구현 가능

### P2-1. 준비 필요시간 메타데이터
- 각 루틴은 대략적인 준비 필요시간을 가진다.
  - `immediate`: 나가기 직전
  - `sameDay`: 당일
  - `previousDay`: 전날
  - `multiDay`: 며칠 전
- 이 메타데이터는 홈 보기 모드와 카피에만 사용한다.
- 체크리스트 상세 안에서는 `전날/당일` 섹션을 강제하지 않는다.

### P2-2. 카테고리 메타데이터
- 각 루틴은 카테고리를 가진다.
  - `daily`: 일상/외출
  - `health`: 건강/운동
  - `family`: 가족/생활
  - `work`: 업무/출장
  - `leisure`: 레저/여행
- 카테고리는 홈 보기 모드와 탐색 보조에만 사용한다.
- 사용자는 카테고리별 보기 안에서도 카드 순서를 바꿀 수 있다.

### P3. 날씨 연동, 선택사항
- 비 오는 날 루틴 자동 제안
- 기온에 따른 외투/장갑/우산 제안
- 단, 외부 API 사용 시 개인정보/위치 권한 없이 지역 수동 선택 우선

### P4. 가족/공유 루틴
- 보호자가 아이 등원 루틴을 만들고 텍스트로 공유
- 공유는 외부 링크 의존 없이 메시지 중심
- 실시간 협업은 후순위

### P5. 알림/리마인더
- 출근 전 체크 알림
- 등원 전 체크 알림
- 병원 예약 전 체크 알림
- 골프/국내여행/해외여행/등산 전날 체크 알림
- Apps in Toss 기능성 메시지/알림 정책 확인 후 적용

### P6. 상황 추천 엔진
- 최근 사용 빈도, 준비 필요시간, 카테고리, 사용자 변경 순서를 기반으로 홈 카드 정렬
- AI 생성이 아니라 규칙 기반 추천으로 정책 리스크 최소화

### P7. 백업/동기화

- 서버 저장 시 최소 데이터만 저장

### P8. 운영/관리
- 개인정보처리방침
- 서비스 이용약관
- 데이터 삭제 기능

## 9. 디자인 / UIUX

### 9.1 디자인 방향
- Toss 스타일: 큰 제목, 짧은 설명, 큰 터치 영역, 부드러운 카드 UI
- 너무 생산성 앱처럼 복잡하지 않게, 준비물 체크에 집중하는 도구로 설계
- 홈은 기본적으로 “위에서 아래로 갈수록 더 미리 준비할 것”이라는 단순한 스크롤 구조를 가진다.
- 사용자는 홈 보기 모드를 `준비 흐름별` 또는 `카테고리별`로 바꿀 수 있고, 각 그룹 안의 카드 순서도 직접 조정할 수 있다.
- 완료감이 중요하지만 과한 게임화/리워드는 금지

### 9.1.1 앱인토스 WebView UX 가이드 반영
- 비게임 미니앱 기본 내비게이션 바를 유지한다. 모든 화면 상단에서 사용자가 현재 서비스를 인지하고 토스로 돌아갈 수 있어야 한다.
- 네비게이션 바 영역과 콘텐츠가 겹치지 않도록 Safe Area top/bottom을 적용한다.
- 외부 웹을 iframe으로 불러오거나 외부 URL로 핵심 기능을 이동시키지 않는다. 핵심 루프는 미니앱 내부에서 완결한다.
- Safe Area와 토스 앱 내 네비게이션 영역을 고려해 `SafeAreaInsets.get/subscribe` 값을 우선 사용하고, CSS fallback으로 `padding-bottom: max(16px, env(safe-area-inset-bottom))` 수준의 하단 여백을 둔다.
- 바텀시트가 열린 상태에서 뒤로가기/스와이프 동작은 먼저 바텀시트를 닫고, 홈에서는 미니앱 종료/이전 화면 정책을 따른다. 이때 `backEvent` 리스너는 컴포넌트 언마운트 시 반드시 해제하고 `onError`를 둔다.
- 앱 진입 직후 자동 바텀시트/알림 동의/광고성 팝업을 띄우지 않는다. 체크리스트 바텀시트는 사용자가 루틴 카드를 탭했을 때만 열린다.
- CTA 문구는 다음 행동을 예측할 수 있게 쓴다. 예: `항목 추가하기`, `체크 지우기`, `기본 준비물로 돌리기`.
- 검색 입력 중 키보드가 올라와도 결과 리스트와 주요 CTA가 가려지지 않도록 visual viewport 변화 또는 TDS/SDK 키보드 대응 컴포넌트를 확인한다.
- 권한 요청은 MVP에서 사용하지 않는다. 위치/알림은 프로덕션 검토 시 필요 순간에 이유를 설명한 뒤 요청한다.

### 9.5 핵심 화면

#### 홈 화면

- 상황 카드: 아이콘 + 제목 + 짧은 설명
  - 출근: `사원증, 충전기, 우산까지`
  - 외출: `집 키, 카드, 보조배터리까지`
  - 운동: `수건이랑 이어폰 챙겼나요?`
  - 비 오는 날: `우산만 챙기면 끝이 아닐 수도 있어요`
  - 골프: `장갑, 거리측정기, 티오프 시간까지`
  - 국내여행: `숙소, 교통편, 충전기까지`
  - 해외여행: `여권, 환전, eSIM까지`
  - 등산: `등산화, 물, 바람막이까지`
- 검색창: `어떤 준비를 찾고 있나요?`
- 홈 보기 모드 선택: `준비 흐름별`, `카테고리별`
- 기본 선택값: `준비 흐름별`
- 그룹 내부 카드 순서 편집 진입: `순서 바꾸기`
- 홈 하단으로 내려갈수록 더 미리 준비할 템플릿이 나오는 구조는 준비 흐름별 정렬의 기본값이다.

#### 체크리스트 바텀시트
- 홈 카드 또는 검색 결과 탭 시 바텀시트로 열린다.
- 상단: 상황 제목 + 완료 상태
- 진행률: `7개 중 4개 완료`
- 리스트: 체크박스 + 항목명
- 하단 보조 CTA: `기본값에서 제공하는 준비물 보기`
- 보조 버튼: `체크만 지우기`
- 사용자 변경값이 있을 때만: `기본값으로 돌리기`
- 항목 편집: `항목 추가`, `삭제`, `순서 변경`

#### 완료 상태
- 전체 완료 시 카드:
  - `다 챙겼어요`
  - `이제 나가도 좋아요.`

### 9.6 접근성 / 해상도
- 기준 설계 폭은 360~420px, 세로 논리 해상도는 360×640~420×740 범위로 잡고, 1x/2x 에셋만 사용한다.
- 테스트 기기는 화면비가 다른 2~3종, Safe Area가 큰 기기 1종, 작은 화면 1종을 포함한다.
- 모든 체크박스에 명확한 label
- 아이콘 단독 버튼 금지
- 삭제 버튼: `운동화 항목 삭제`처럼 구체적 레이블
- 진행률은 텍스트로도 표시
- 체크 상태는 색상뿐 아니라 체크 아이콘/텍스트로 표시
- 터치 영역 44px 이상
- 순서 변경 버튼은 `골프 카드를 위로 이동`, `골프 카드를 아래로 이동`처럼 읽히고, 첫/마지막 항목의 불가능한 이동 버튼은 disabled 처리한다.
- 순서 변경 후 focus는 이동한 카드 또는 다음 이동 버튼에 유지한다.
- 폰트 확대 시 카드가 깨지지 않도록 line-height 확보

## 10. 데이터 모델

```ts
type SituationId =
  | 'commute'
  | 'outing'
  | 'workout'
  | 'rainy'
  | 'hospital'
  | 'grocery'
  | 'childSchool'
  | 'businessTrip'
  | 'golf'
  | 'camping'
  | 'domesticTravel'
  | 'overseasTravel'
  | 'hiking';

type PrepTimeCategory = 'immediate' | 'sameDay' | 'previousDay' | 'multiDay';

type PrepFlowGroup = 'now' | 'todayTomorrow' | 'early'; // 화면 그룹: 지금, 오늘·내일, 미리

type RoutineCategory = 'daily' | 'health' | 'family' | 'work' | 'leisure';

type HomeSortMode = 'prepFlow' | 'category';

type TemplateItem = {
  id: string; // deterministic: golf-shoes, commute-wallet
  label: string;
  sortOrder: number;
};

type TemplateRoutine = {
  situationId: SituationId;
  title: string; // 명사형 표시명: 출근, 병원, 골프
  prepTimeCategory: PrepTimeCategory; // 내부 메타데이터
  prepFlowGroup: PrepFlowGroup; // 화면 그룹과 카드 순서 저장 기준
  category: RoutineCategory;
  tags: string[];
  defaultCardOrder: number;
  defaultItems: TemplateItem[];
};

type UserItem = {
  id: string; // custom-${timestamp}-${randomOrUuid}
  label: string;
  sortOrder: number;
  createdAt: string;
};

type UserRoutineOverride = {
  situationId: SituationId;
  customItems: UserItem[];
  customItemOrder?: string[];
  updatedAt: string;
};

type SessionCheckState = {
  situationId: SituationId;
  checkedItemIds: string[]; // 기본적으로 영구 저장하지 않음
};

type RecentRoutine = {
  situationId: SituationId;
  lastUsedAt: string;
};

type AppStorage = {
  schemaVersion: 1;
  userRoutineOverrides: Partial<Record<SituationId, UserRoutineOverride>>;
  recent: RecentRoutine[];
  homeSortMode: HomeSortMode;
  cardOrderByPrepFlow?: Partial<Record<PrepFlowGroup, SituationId[]>>;
  cardOrderByCategory?: Partial<Record<RoutineCategory, SituationId[]>>;
};
```

### 10.1 저장/병합 규칙

- `TemplateRoutine`은 앱 코드에 포함되는 기본 템플릿 원본이다.
- Storage key namespace는 `what-to-bring:v1:app-storage` 하나를 기본으로 하고, 마이그레이션 필요 시 `schemaVersion`으로 분기한다.
- `UserRoutineOverride`만 Apps in Toss Storage에 저장한다.
- 화면 표시 시 `TemplateRoutine.defaultItems + UserRoutineOverride.customItems`를 병합한다.
- 체크 상태는 `SessionCheckState`로만 관리하고 Storage에 저장하지 않는다. 바텀시트 닫힘 또는 앱 재진입 시 초기화한다.
- Storage JSON 파싱 실패, quota 초과, API 오류 시 기본 템플릿으로 fallback하고 `저장된 변경값을 불러오지 못했어요. 기본 준비물로 보여드릴게요.` 안내를 보여준다.
- 기본 항목 id는 변경하지 않는다. 템플릿이 업데이트되어도 같은 id는 같은 준비물로 본다.
- 커스텀 항목 id는 생성 시 고유하게 만들고, 라벨 중복은 `trim + 연속 공백 정규화` 후 같은 루틴 안에서 방지한다.
- 스키마 변경 시 `schemaVersion` 기준으로 마이그레이션한다.

### 10.2 Analytics 이벤트 계약

이벤트명은 아래 표를 canonical event contract로 고정한다. SDK별 차이는 `analytics.ts` 래퍼에서만 흡수하고, PRD/테스트/전환 지표는 이 이벤트명을 기준으로 한다.

| 이벤트 | 트리거 | 허용 payload | 금지 payload |
|---|---|---|---|
| `select_routine` | 홈/검색 결과에서 루틴 카드 탭 | `routine_id`, `source: home/search/recent`, `view_mode`, `group_id` | 사용자 입력 항목명 |
| `view_bottom_sheet` | 체크리스트 바텀시트 오픈 | `routine_id`, `item_count`, `custom_item_count` | 체크리스트 상세 라벨 전체 |
| `check_item` | 체크박스 체크/해제 | `routine_id`, `item_type: default/custom`, `checked`, `checked_count` | 항목명 |
| `search_routine` | 검색 실행 또는 결과 확정 | `query_type: routine/category/tag/unknown`, `result_count`, `matched_routine_ids` 최대 5개 | raw 검색어 |
| `add_custom_item` | 커스텀 항목 추가 성공 | `routine_id`, `custom_item_count` | 커스텀 항목명 |
| `reset_to_default` | 루틴 기본값 복원 | `routine_id`, `custom_item_count_before` | 삭제된 항목명 |
| `view_default_items` | 기본값 제공 준비물 보기 | `routine_id`, `default_item_count` | 기본 항목 전체 배열 |
| `reorder_card` | 그룹 내부 카드 순서 변경 | `view_mode`, `group_id`, `routine_id`, `direction` | 없음 |
| `complete_routine` | 모든 항목 체크 완료 | `routine_id`, `total_count`, `custom_item_count` | 항목명 |

전환 지표 후보는 `check_item` 1회 이상을 핵심 전환으로 두고, `complete_routine`은 보조 전환으로 둔다. 챌린지 AU 판단은 토스 콘솔 대시보드를 기준으로 하며, 이벤트 데이터는 UX 개선/설명 근거로 사용한다.

구현 래퍼 기준:
```ts
type AnalyticsEventName =
  | 'select_routine'
  | 'view_bottom_sheet'
  | 'check_item'
  | 'search_routine'
  | 'add_custom_item'
  | 'reset_to_default'
  | 'view_default_items'
  | 'reorder_card'
  | 'complete_routine';

function logEvent(name: AnalyticsEventName, payload: Record<string, string | number | boolean | string[]>): void;
```
`logEvent`는 내부에서 설치 SDK가 제공하는 `Analytics.Press`/`Impression` 또는 `Analytics.click`/`impression` 중 실제 지원 API로 변환한다.

| 날씨 API 범위 증가 | 중간 | MVP 제외. 비 오는 날은 수동 상황 카드로 처리 |
| 구현 일정 부족 | 높음 | 서버/로그인/알림/AI 모두 제외하고 로컬 우선 MVP 고정 |
| Toss SDK 빌드 불확실성 | 중간 | 첫 작업을 공식 템플릿 생성/빌드 확인으로 둠 |

## 12.1 서비스 제작 보완 추천

아래 항목은 PRD의 제품 방향과 직접 충돌하지 않지만, 실제 서비스 제작·심사·운영 단계에서 빠지면 문제가 될 수 있다.

| 보완 항목 | 필요성 | 추천 적용 |
|---|---|---|
| 검색 UX | 태그를 추가했으므로 사용자가 `라운딩`, `스크린`, `해외여행`으로도 루틴을 찾을 수 있어야 함 | MVP에는 홈 상단 간단 검색 또는 v0.2 후보로 명시. 구현 여유가 없으면 태그는 데이터에만 보유 |
| 로컬 저장 안내 | 사용자가 직접 쓴 준비물은 민감 정보가 될 수 있음 | 설정/안내에 `입력한 준비물은 이 기기의 앱 저장소에 저장돼요` 문구 추가 |
| 삭제/초기화 UX | 사용자 데이터가 로컬에 남는지 불안할 수 있음 | MVP에는 루틴별 `기본값으로 돌리기`, 프로덕션에는 `저장된 루틴 전체 삭제` 제공 |
| 템플릿 업데이트 병합 | 기본 템플릿이 개선될 때 사용자 항목과 충돌 가능 | `schemaVersion`, deterministic item id, 사용자 override 분리 유지 |
| 측정/분석 | 토스 콘솔에서 확인 가능한 지표와 앱 내 직접 이벤트를 연결해야 대회 심사/개선 근거가 생김 | MVP부터 설치 SDK 기준 Analytics 이벤트 래퍼를 최소 세트로 심고, 출시 후 콘솔 대시보드/전환 지표로 확인 |
| 접근성 QA | 체크박스/순서변경 UI는 스크린리더 혼란 가능 | 버튼 label을 `골프 카드를 위로 이동`처럼 구체화 |
| 정책 고지 | 병원 카드가 의료 서비스로 오해될 수 있음 | `준비물 체크 전용이며 진료/예약/추천을 제공하지 않음` 명시 |
| 템플릿 품질 | 골프/캠핑/국내여행/해외여행/등산은 누락 항목 체감이 큼 | 커뮤니티 불편 문장 수집 후 템플릿 항목 보강 |
